## 二、各阶段目标、原则、适用边界及衔接关系

### Phase 1：BMAD 目标与决策对齐阶段

| 维度 | 内容 |
|------|------|
| **目标** | 建立项目愿景共识、明确角色职责、锁定决策权归属、形成可执行的任务路线图 |
| **核心原则** | ① 先对齐再行动；② 决策记录透明可追溯；③ 角色边界清晰无歧义 |
| **适用边界** | 适用于项目启动、需求变更决策、跨团队协作冲突解决；不适用于纯技术实现细节 |
| **衔接** | 输出"已对齐的目标集 + 决策日志" → 作为 Phase 2 规格编写的约束输入 |

**BMAD 方法论四步法：**

| 步骤 | 含义 | 交付物 |
|------|------|--------|
| **B**ackground (背景锚定) | 定义 Why — 为什么做这个项目 | 项目愿景声明 |
| **M**odel (角色建模) | 定义 Who — 谁负责什么决策 | RACI 矩阵 |
| **A**lign (目标对齐) | 定义 What — 成功标准与优先级 | OKR/目标清单 |
| **D**ecide (决策框架) | 定义 How — 决策流程与升级路径 | 决策日志模板 |

### Phase 2：SDD 规格建立阶段

| 维度 | 内容 |
|------|------|
| **目标** | 将原型转化为机器可读、人类可评审的结构化规格文档，建立系统契约 |
| **核心原则** | ① 规格即真相源 (SSOT)；② 契约优先，实现滞后；③ 可验证性 |
| **适用边界** | 适用于接口定义、数据模型、业务规则的形式化描述；不适用于视觉设计微调 |
| **衔接** | 输出"规格文档 + 接口契约" → 作为 Phase 3 设计与 Phase 4 实现的硬约束 |

### Phase 3：系统设计 + 契约验证阶段

| 维度 | 内容 |
|------|------|
| **目标** | 基于规格完成架构设计、模块划分、技术选型，并通过契约测试验证设计一致性 |
| **核心原则** | ① 设计必须可追溯到规格条目；② 架构决策需记录权衡 (ADR)；③ 接口向后兼容 |
| **适用边界** | 适用于系统架构、模块交互、数据流设计；不适用于具体代码实现 |
| **衔接** | 输出"架构文档 + 模块接口清单 + ADR" → 作为 Phase 4 TDD 循环的设计输入 |

### Phase 4：TDD 驱动实现阶段

| 维度 | 内容 |
|------|------|
| **目标** | 通过 Red-Green-Refactor 循环实现高置信度代码，确保每行代码都有测试保护 |
| **核心原则** | ① 没有失败的测试就不写生产代码；② 测试即文档；③ 小步快跑、持续重构 |
| **适用边界** | 适用于业务逻辑实现、算法开发、集成层编码；原型验证期或一次性脚本可放宽 |
| **衔接** | 输出"通过测试的代码 + 测试报告" → 作为 Phase 5 交付验证的实现基础 |

### Phase 5：交付与运营反馈阶段

| 维度 | 内容 |
|------|------|
| **目标** | 完成端到端验收、部署上线、建立运营监控与反馈闭环 |
| **核心原则** | ① 交付物可追溯到规格条目；② 上线即监控；③ 反馈驱动迭代 |
| **适用边界** | 覆盖发布部署、验收测试、生产运维、需求迭代回流 |
| **衔接** | 输出"验收报告 + 运维看板 + 迭代 Backlog" → 回流至 Phase 1 下轮对齐 |

## 三、从 Axure 原型中提取需求、梳理流程、拆解模块、形成规格的方法

### 3.1 原型解析工作流

```
Axure 在线原型
      ▼
Step 1: 结构提取
   - 导出页面地图 (Sitemap)
   - 提取所有标注/批注
   - 抓取交互事件配置 (OnClick/OnChange 等)
   - 导出组件矩阵（表单、表格、弹窗、导航等）
      ▼
Step 2: 用户流程梳理
   - 识别角色与权限边界
   - 还原核心任务流 (Happy Path + Edge Cases)
   - 标注状态转换节点
   - 建立页面跳转有向图
      ▼
Step 3: 功能模块拆解
   - 按业务域分组 (用户管理、订单、支付…)
   - 按技术层分组 (前端组件、BFF、领域服务、数据层)
   - 识别共享能力 (公共组件、通用校验规则)
   - 建立模块依赖关系图
      ▼
Step 4: 规格文档生成
   - 每个模块 → 功能需求条目 (FR-xxx)
   - 每条流程 → 用户故事 (US-xxx)
   - 每个交互 → 验收标准 (AC-xxx)
   - 全局约束 → 非功能需求 (NFR-xxx)
```

### 3.2 原型映射表（核心交付物示例）

| 原型页面/组件 | 模块归属 | 用户故事 | 验收标准 | API 端点 | 数据实体 | 优先级 | 状态 |
|--------------|---------|---------|---------|---------|---------|--------|------|
| P01-登录页 | auth-module | US-001 | AC-001~003 | POST /api/auth/login | User, Session | P0 | 已规格化 |
| P03-商品列表 | product-module | US-005 | AC-010~015 | GET /api/products | Product, Category | P0 | 已规格化 |

### 3.3 AI Agent 在原型解析阶段的职能

| 职能 | 具体动作 |
|------|---------|
| **原型转文本** | 读取 Axure 导出的 HTML/Sitemap，自动提取页面标题、组件、交互描述 |
| **流程补全** | 根据已有页面识别断裂的用户路径，提示缺失流程 |
| **PRD 草稿生成** | 基于结构化提取结果，自动生成产品需求文档草稿 |
| **一致性校验** | 检查命名一致性、交互模式统一性、遗漏状态标注 |

## 四、BMAD / SDD / TDD 三大方法的分工与协同

### 4.1 BMAD — 目标与决策对齐

| 应用场景 | 实施方法 |
|---------|---------|
| 项目启动对齐 | 组织 BMAD Workshop：Background → Model → Align → Decide 四步工作坊 |
| 需求优先级决策 | 使用 WSJF 评分 + RACI 确认决策者 |
| 变更影响评估 | 变更请求进入时触发 BMAD Decision Gate，评估影响域并记录 ADR |
| 跨团队冲突解决 | 升级至 RACI 中定义的 Accountable 角色，限期决策 |

**AI Agent 职能**：自动生成会议纪要、维护决策日志、追踪待决事项、预警决策超期。

### 4.2 SDD (SPEC KIT) — 建立规范与契约

| 层级 | 规格内容 | 工具/格式 |
|------|---------|----------|
| **L1: 需求规格** | 功能需求、非功能需求、约束条件 | Markdown + Requirement ID |
| **L2: 接口契约** | REST/GraphQL API、事件协议、SDK 接口 | OpenAPI 3.0 / AsyncAPI / Protobuf |
| **L3: 数据模型** | 实体关系、字段约束、数据流转 | ER Diagram + JSON Schema |
| **L4: 行为规格** | 状态机、业务规则、计算公式 | BDD (Gherkin) + 决策表 |
| **L5: 架构规格** | 部署拓扑、服务边界、技术栈约束 | ADR + C4 Model |

**SPEC KIT 工作流：**

```
需求条目 → 规格编写 → 规格评审 → 契约锁定 → 实现绑定 → 契约测试 → 变更管理
    ▲                                                              │
    └──────────── 变更请求回流 ◀───────────────────────────────────┘
```

**AI Agent 职能**：自动生成 OpenAPI Spec、从用户故事生成 Gherkin Feature 文件、检测契约冲突、维护版本兼容性矩阵。

### 4.3 TDD — 测试先行与实现迭代

**Red-Green-Refactor 循环：**

```
1. RED: 编写失败测试
   - 从 AC (验收标准) 转换为测试用例
   - 先单元级，再集成级
   - 命名: should_[预期行为]_when_[条件]
2. VERIFY RED: 确认测试因功能缺失而失败（非编译错误）
3. GREEN: 只写让测试通过的最少代码，禁止投机性扩展
4. REFACTOR: 消除重复、改善命名与抽象，保持测试全绿
5. 循环 → 下一个 AC
```

**TDD 分层实施：**

| 测试层级 | 覆盖目标 | 工具 | 占比目标 |
|---------|---------|------|---------|
| 单元测试 | 函数/类逻辑正确性 | Jest/Pytest/JUnit | 70% |
| 集成测试 | 模块间交互、数据库操作 | Testcontainers/MSW | 20% |
| 端到端测试 | 关键用户流程 | Playwright/Cypress | 10% |

**AI Agent 职能**：从验收标准自动生成测试用例、识别未覆盖分支、生成 Mock/Stub 代码、Refactor 建议、检测测试脆弱性。

## 六、软件生命周期管理机制

### 6.1 全景流程

```
需求管理 → 设计评审 → 开发实施 → 测试验证 → CI/CD → 发布部署 → 验收交付 → 运营反馈
    ▲                                                                         │
    └─────────────────────── 迭代闭环 ◀──────────────────────────────────────┘
```

### 6.2 各阶段管理机制

| 阶段 | 管理机制 | 门禁条件 | 度量指标 |
|------|---------|---------|---------|
| 需求管理 | Backlog 优先级 + BMAD Decision Gate | 唯一 ID + AC + 负责人 | 需求覆盖率、变更频率 |
| 设计评审 | 规格驱动评审 + Checklist | 契约无冲突、ADR 已记录 | 评审问题密度、返工率 |
| 开发实施 | TDD 循环 + 每日构建 | 测试全绿、Lint 通过、覆盖率达标 | 代码覆盖率、构建通过率 |
| 测试验证 | 分层测试 + 契约测试 | P0/P1 全通过、Critical Bug 清零 | 缺陷密度、逃逸率 |
| CI/CD | GitOps、自动化 Pipeline | 所有阶段 Pipeline 绿灯 | 部署频率、变更前置时间 |
| 发布部署 | 金丝雀/蓝绿发布 | 健康检查通过、回滚方案就绪 | 部署成功率、MTTR |
| 验收交付 | 需求-测试-交付物三向追溯 | 100% 覆盖、所有 AC 通过 | 验收一次通过率 |
| 运营反馈 | 埋点 + 用户反馈回流 Backlog | NPS 监控、SLA 达标 | 用户满意度、可用性 |

### 6.3 CI/CD Pipeline 设计

```yaml
Pipeline Stages:
  1. Code Quality:    Lint → Static Analysis → Security Scan (SAST)
  2. Unit Test:       Run Unit Tests → Coverage Threshold (≥80%)
  3. Integration:     Contract Test → DB Migration Test → API Test
  4. Build:           Compile/Bundle → Docker Image → Push Registry
  5. Deploy-Staging:  Apply Manifests → Smoke Test → E2E Test
  6. Deploy-Prod:     Canary (5%→25%→100%) → Health Check → Auto-Rollback
  7. Post-Deploy:     Monitor 30min → Report → Close Sprint
```

### 7.1 SRS 质量检查清单示例

- [ ] 所有需求条目有唯一 ID 且格式统一 (FR-module-序号)
- [ ] 每条 FR 至少关联 1 条 AC (Given/When/Then)
- [ ] 需求间无矛盾（AI 一致性扫描通过）
- [ ] 明确的 Out-of-Scope 声明
- [ ] 非功能需求有量化指标（响应时间 ≤ 200ms P95）
- [ ] 与原型映射表交叉验证覆盖率 = 100%

## 八、跨角色协作模式与决策流程

### 8.1 角色定义与协作界面

```
产品经理 ↔ UI/UX设计 ↔ 架构/开发 ↔ 测试 ↔ PMO
                  (AI Agent 全程支撑)
```

### 8.2 决策流程（RACI + BMAD Gate）

| 决策类型 | Responsible | Accountable | Consulted | Informed | 决策方式 |
|---------|------------|-------------|-----------|----------|---------|
| 需求优先级 | BA/PM | Product Owner | Dev Lead, QA Lead | 全团队 | BMAD Align Workshop |
| 技术方案选型 | Dev Lead | Architect | PM, QA, DevOps | 全团队 | ADR + Design Review |
| 接口契约变更 | Backend | Architect + Frontend Lead | QA, 产品 | 全团队 | 契约评审会 |
| 发布窗口 | DevOps | PM | QA, 产品, 业务方 | 全团队 | BMAD Decision Gate |
| 缺陷修复优先级 | QA Lead | PM | Dev Lead | 开发团队 | 每日站会 + Triage |

### 8.3 AI Agent 定位

- 不承担 Accountable 角色，其定位为 **Support/Accelerate**
- 自主执行：格式检查、覆盖率计算、一致性扫描、文档汇编
- 需人工授权：代码提交、环境部署、需求状态变更

## 九、风险控制点、质量门禁、度量指标与回退策略

### 9.1 风险登记册模板

| ID | 风险描述 | 概率 | 影响 | 应对策略 | 负责人 | 触发条件 | 状态 |
|----|---------|------|------|---------|--------|---------|------|
| R01 | 原型标注不完整导致需求遗漏 | 中 | 高 | AI 覆盖率扫描 + 人工走查 | BA | 映射表覆盖 <95% | 监控中 |
| R02 | 契约频繁变更导致返工 | 中 | 高 | 契约冻结 + 变更走 BMAD Gate | Architect | 单 Sprint 变更 >3 次 | 预防中 |
| R03 | AI 生成代码质量不达标 | 低 | 高 | 人工 Review 不可跳过 + TDD 保障 | Dev Lead | 缺陷密度 >阈值 | 监控中 |

### 9.2 质量门禁

- **DoR (Definition of Ready)**：故事进入开发前，AC、估算、依赖、原型链接全部到位
- **DoD (Definition of Done)**：合并前，测试全绿、覆盖率达标、Review 通过、文档更新
- **发布门禁**：Staging E2E 全通过、回滚 Runbook 就绪、灰度方案确认

### 9.3 回退策略

- 灰度期指标异常 → 自动回滚至上一稳定版本
- 契约破坏性变更 → 保留旧版本 Endpoint + Deprecated 头 + 迁移窗口
- AI 生成结果异常 → 一键切换到人工兜底实现路径

## 十三、落地执行建议

1. **渐进式导入**：首个 Sprint 先跑通 Phase 1→2→4 主干，Phase 3 简化为轻量 ADR；后续逐步补全。
2. **AI Agent 信任建设**：初期所有 AI 产出 100% 人工审核；信任建立后，低风险产出可授权 AI 自主完成。
3. **规格冻结窗口**：每 Sprint 进入 Phase 4 前锁定契约，变更需走 BMAD Gate。
4. **原型与规格同步**：Axure 每次更新触发 AI 自动 Diff 分析 + 影响报告。
5. **知识沉淀**：决策日志、ADR、踩坑记录持续积累，AI Agent 作为项目知识库检索入口。
